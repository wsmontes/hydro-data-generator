# UI Phase 2 — User Editing & Protection Model

Status: active
Parent audit: `docs/UI_DATA_VISIBILITY_EDITABILITY_AUDIT.md`
Previous phase: `docs/UI_PHASE_1_ITEM_DETAIL_VISIBILITY_MAP.md`
Area: user edits, provenance, protected fields, AI reprocessing behavior
Last updated: 2026-06-10

This document audits and defines the user editing and protection model for wawa-note.

The central question:

> When the user edits information, does the system truly treat that information as user-owned and protected, or does it only appear that way in the UI?

---

## 1. Product Rule

User edits are not cosmetic.

When a user edits a field, the edit must change the ownership status of that field.

From that point forward:

```text
AI must not overwrite the field directly.
AI may suggest changes.
The user must review and accept/reject/merge suggestions.
```

This should apply to every meaningful field, not only note body text.

---

## 2. Current Evidence from Code

## 2.1 NoteEditorView marks user ownership

File:

```text
wawa-note/UI/Knowledge/NoteEditorView.swift
```

Observed behavior:

On create:

```swift
var prov = item.provenance
prov.mark(field: "title", origin: .user)
if item.bodyText != nil { prov.mark(field: "bodyText", origin: .user) }
item.fieldProvenanceJSON = prov.encode()
```

On edit:

```swift
var prov = item.provenance
prov.mark(field: "title", origin: .user)
if bodyText.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty == false {
    prov.mark(field: "bodyText", origin: .user)
}
item.fieldProvenanceJSON = prov.encode()
```

This is good.

It means the app already has a concept of field provenance and user ownership.

Primary limitation:

This pattern is currently visible only for title/body text in note-style editing.

---

## 2.2 KnowledgeDetailView promises protected reprocessing

File:

```text
wawa-note/UI/Knowledge/KnowledgeDetailView.swift
```

Observed behavior:

The reprocess warning says:

```text
You have manually edited this item's content. Re-processing will re-analyze it. Your edits will be protected and AI may suggest changes for your review instead of overwriting them.
```

This is the correct product promise.

Primary risk:

The UI promise must be enforced by the pipeline and artifact writers.

If the pipeline still writes over protected fields or artifacts, the UI message becomes misleading.

---

## 2.3 Project intention marks manual ownership

File:

```text
wawa-note/UI/Project/ProjectDetailView.swift
```

Observed behavior:

When the user edits project intention, code sets:

```swift
project.intention = trimmed.isEmpty ? nil : trimmed
project.intentionIsAutoGenerated = false
```

This is another good ownership pattern.

Primary limitation:

It uses a specific boolean rather than a shared field ownership/provenance model.

## 3. Current Design Strengths

### Strength 1 — The app already thinks in provenance

The existence of:

```text
item.provenance
fieldProvenanceJSON
prov.mark(field:origin:)
```

is a strong foundation.

### Strength 2 — User edit protection is already part of product language

The reprocess warning already expresses the correct behavior.

### Strength 3 — Project intention distinguishes AI vs user

`intentionIsAutoGenerated = false` is a simple but useful ownership signal.

## 4. Major Gaps

## Gap 1 — Protection appears field-limited

Currently confirmed protected fields:

```text
title
bodyText
project.intention via separate boolean
```

Fields that also need protection:

```text
transcript
summary
analysis.shortSummary
action items
risks
doubts
signals
tags
item type
context metadata
project assignment
relationships/backlinks
task title/description/status
OCR text
bookmark metadata
```

### Required change

Provenance must become universal across user-visible fields.

---

## Gap 2 — Artifacts are not clearly part of field ownership

Important data lives outside the main SwiftData model:

```text
transcript.json
analysis.json
raw analysis JSON
recording manifest
OCR output
processing reports
```

If the user edits transcript or summary, where is that stored?

Possible options:

1. overwrite artifact and mark artifact field provenance;
2. store corrected artifact beside original;
3. store user override in SwiftData model;
4. store patch/diff.

### Required decision

Each artifact must have an ownership strategy.

Recommended:

```text
original AI/generated artifact remains available
user-corrected artifact becomes active source of truth
field-level provenance marks corrected fields as user-owned/protected
future AI output becomes suggestion artifact
```

---

## Gap 3 — Reprocess warning may not equal enforcement

The warning claims protected fields will not be overwritten.

Need audit:

- Does `ContentPipelineService` inspect field provenance?
- Does it avoid overwriting `bodyText` if user-owned?
- Does it avoid overwriting title if user-owned?
- Does it write analysis suggestions separately?
- Does it overwrite `analysis.json`?
- Does it overwrite `transcript.json`?
- Does re-transcription overwrite corrected transcript?

### Required change

Create an explicit write policy layer.

## 5. Required Write Policy

Add a shared field/artifact write policy used by all AI/pipeline code.

Suggested type:

```swift
struct FieldWriteDecision {
    enum Action {
        case writeDirectly
        case writeAsSuggestion
        case skip
        case conflict
    }

    let action: Action
    let reason: String
}
```

Suggested service:

```swift
enum FieldWritePolicy {
    static func decide(
        item: KnowledgeItem,
        field: String,
        proposedOrigin: ProvenanceOrigin,
        isUserInitiated: Bool
    ) -> FieldWriteDecision
}
```

Rules:

```text
If field has user origin/protected status and proposed origin is AI:
    write as suggestion, not direct overwrite.

If field is empty/unowned and proposed origin is AI:
    write directly.

If write is user-initiated:
    write directly and mark user/protected.

If field is imported and user has not edited:
    AI may enrich but should not destroy original source.
```

## 6. Protected Field Behavior

When a field is protected:

### Direct write is blocked

AI cannot do this:

```text
protected bodyText -> replace with generated text
protected transcript -> replace with new transcription
protected summary -> replace with new summary
```

### AI output becomes a suggestion

Store suggestion separately:

```text
suggestions/{field}/{timestamp}.json
```

or as SwiftData `AgentSuggestion` with field target.

### User gets review UI

```text
AI suggested an update to your protected summary.
Actions: Accept, Reject, Compare, Merge
```

---

## 7. Required Provenance Model

The current provenance model needs to be visible enough to support UI and policy.

Suggested conceptual model:

```swift
enum FieldOrigin: Codable {
    case user
    case ai
    case imported
    case transcription
    case ocr
    case system
}

struct FieldProvenanceEntry: Codable {
    let field: String
    let origin: FieldOrigin
    let isProtected: Bool
    let updatedAt: Date
    let updatedBy: String?
    let sourceArtifact: String?
}
```

If current implementation differs, align conceptually rather than renaming everything immediately.

## 9. Required Editing Flows

## 9.1 Title edit

- always available;
- user save marks title user/protected;
- AI title suggestions go to suggestion queue.

## 9.2 Body text edit

- current note editor behavior is good baseline;
- must show save errors;
- user edits mark bodyText user/protected;
- reprocess uses bodyText as trusted input.

## 9.3 Transcript correction

- user edits transcript;
- original transcript remains stored;
- corrected transcript becomes active transcript;
- transcript marked user/protected;
- analysis should use corrected transcript;
- re-transcription writes suggestion, not overwrite.

## 9.4 Summary edit

- user edits summary;
- summary marked user/protected;
- re-analysis writes suggested summary;
- user can accept/reject/merge.

## 9.5 Action item edit

- user can edit extracted action item before converting to task;
- conversion creates user-owned task;
- future AI action item changes do not modify task directly.

## 9.6 Metadata edit

- user can edit context fields;
- metadata marked user/protected;
- future import/AI inference becomes suggestion.

## 10. Save Error Policy

Current code often uses `try?` in user-visible save paths.

This is risky.

When user taps Save:

```text
failure must be visible
screen must not dismiss as if save succeeded
```

Recommended pattern:

```swift
do {
    try modelContext.save()
    dismiss()
} catch {
    saveError = error.localizedDescription
}
```

UI:

```text
Could not save changes.
Try again.
```

This applies to:

- note save;
- title/body edit;
- project intention edit;
- relationship creation;
- metadata edit;
- tag edit;
- transcript correction;
- summary edit.

---

## 11. Reprocess Policy

Reprocess must be explicit about input and output.

### Before reprocess

UI should show:

```text
Re-analyze from:
- corrected transcript
- body text
- OCR text
- audio transcript
```

and:

```text
Protected fields will not be overwritten.
New AI output will appear as suggestions.
```

### During reprocess

Pipeline must use write policy for every output field.

### After reprocess

If suggestions were created:

```text
AI suggested 3 updates
Review suggestions
```

## 12. AI Suggestion Model

Suggested fields for `AgentSuggestion` or equivalent:

```swift
struct FieldSuggestion {
    let id: UUID
    let itemId: UUID
    let fieldPath: String
    let currentValue: String?
    let suggestedValue: String
    let reason: String?
    let sourceArtifact: String?
    let createdAt: Date
    let status: SuggestionStatus
}

enum SuggestionStatus {
    case pending
    case accepted
    case rejected
    case merged
}
```

Examples:

```text
fieldPath = transcript.text
fieldPath = analysis.shortSummary
fieldPath = tags
fieldPath = project.intention
fieldPath = metadata.date
```

## 16. Summary

The app already contains the beginning of the correct ownership model.

`NoteEditorView` proves the concept: user edits can mark field provenance.

But the product promise is bigger than notes.

The next implementation step is to make field ownership universal and enforce it in the pipeline:

```text
User edit = protected truth.
AI output = suggestion when it conflicts with protected truth.
```
