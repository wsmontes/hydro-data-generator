# UI Data Visibility & Editability Audit

Status: active
Area: User-facing information, editing, review, and data ownership
Last updated: 2026-06-10

This document starts a new audit track for wawa-note: how much information the user can see, understand, edit, correct, protect, and act on inside the UI.

The central product question:

> Does the UI let the user own their information, or does it merely show AI-generated output as a finished artifact?

---

## 1. Scope

This audit covers:

- what data is visible in the UI;
- what data is hidden or only indirectly accessible;
- what fields are editable;
- what fields are read-only;
- where AI-generated information should be reviewable;
- where user edits should be protected;
- what is missing for trust, correction, and ownership.

This is separate from recording reliability.

---

## 2. Current Evidence from Code

### Knowledge detail screen

File:

`wawa-note/UI/Knowledge/KnowledgeDetailView.swift`

Observed capabilities:

- Shows header with title, type, created date, duration, and badges.
- Shows processing / transcription progress.
- Shows transcription errors.
- Shows audio player when playable audio exists.
- Shows artifact sections when transcript or analysis exists.
- Shows image/OCR section for image items.
- Shows body text for notes, journals, and non-image items with `bodyText`.
- Shows context metadata as read-only display.
- Shows raw LLM response in developer mode under a narrow condition.
- Shows annotations and backlinks.
- Allows editing only when `item.bodyText != nil`.
- Editing mode appears to cover title and body content, not all item artifacts.
- Export is available only when `hasExportableContent` is true.

Primary issue:

The detail screen is rich, but editability is conditional and uneven. Important user-facing information such as transcript, summary, analysis, extracted action items, tags, context fields, relationships, and provenance are not clearly first-class editable/reviewable data.

---

### Note editor

File:

`wawa-note/UI/Knowledge/NoteEditorView.swift`

Observed capabilities:

- Provides a proper creation/editing UI for note and journal content.
- Allows editing title and body text.
- Uses `TextEditor` for body.
- Saves via `KnowledgeItemService`.
- Marks title and bodyText provenance as user-created/user-edited.
- Enqueues processing when created item has body content.

Primary issue:

This is the best current example of user ownership, but it appears isolated to notes/journals. The same ownership pattern is not consistently available for transcript, analysis, context fields, AI suggestions, tags, extracted tasks, or imported data.

---

### Project detail screen

File:

`wawa-note/UI/Project/ProjectDetailView.swift`

Observed capabilities:

- Project home view shows header, metrics, health, signals, and recent activity.
- Allows editing the project intention.
- Marks project intention as user-provided by setting `intentionIsAutoGenerated = false`.
- Provides actions to add items, record audio, add note, import file, and export project JSON/Markdown.
- Shows project status as a badge.

Primary issue:

Project intention editability is good, but other important project data appears mostly presentational: status, health, signals, tasks breakdown, item breakdown, alerts, and derived interpretation are not clearly reviewable/editable from the project home.

---

### Home and import flow

File:

`wawa-note/UI/Home/HomeView.swift`

Observed capabilities:

- Handles file import, staged import preview, shared directory import, audio import, text import, image import.
- Enqueues processing after imports.
- Shows import progress and import errors.
- Navigates to item detail after import.

Primary issue:

The import path seems focused on getting content into the system and processing it. It is less clear that the user gets a structured review step for extracted data before it becomes part of the knowledge base.

## 3. High-Level Diagnosis

The app already has data richness, but user agency is inconsistent.

There are three current layers:

```text
1. Raw captured/imported data
2. AI/extraction artifacts
3. User-owned corrections/decisions
```

The UI shows some of layer 1 and layer 2, but layer 3 is not consistently represented.

The product promise should be:

> The user can see what the app knows, correct it, protect corrections, and decide what becomes trusted knowledge.

Right now, the app often behaves like:

> The system processed something; here is the result.

It needs to become:

> Here is what was captured, here is what AI inferred, here is what you accepted/edited/rejected, and here is what is now trusted.

## 4. Data Visibility Matrix

| Data type | Currently visible? | Currently editable? | Problem |
|---|---:|---:|---|
| Item title | Yes | Sometimes | Editable in detail only when `bodyText != nil`; editable in NoteEditor |
| Body text | Yes for notes/journals/body items | Yes for notes/body items | Good but limited to `bodyText` model |
| Audio file | Yes if playable | No | Can play/export, not inspect artifact health |
| Transcript | Yes when artifact exists | Not clearly | User needs correction flow |
| Summary | Yes as analysis | Not clearly | Needs accept/edit/protect flow |
| Action items | Likely visible in analysis | Not clearly | Should be promotable/editable as tasks |
| Tasks | Visible in project/task views | Probably editable elsewhere | Need audit separately |
| Tags | Visible in some places | Not clearly | Tag editing/management not obvious |
| Context metadata | Visible read-only | No | User should correct source/date/location/project/context |
| AI signals | Visible in project | Not clearly | Need accept/dismiss/convert-to-task/doubt flow |
| Backlinks/relationships | Visible | Limited creation via Connect | Need relation management/edit/delete/explain provenance |
| Provenance | Stored in code | Mostly hidden | User needs visible ownership/protection indicators |
| Raw LLM JSON | Developer-only edge case | No | Useful debug, not user-facing |
| Processing status | Visible | No | Needs retry/diagnose controls |

## 5. Core UX Problems

### Problem 1 — Edit button appears only for items with `bodyText`

If an item has no `bodyText`, the detail toolbar may not show Edit.

This excludes many important item types:

- audio-only item with transcript;
- imported file without bodyText;
- analysis-only item;
- image item where OCR appears elsewhere;
- web bookmark with derived metadata;
- item whose meaningful content is in artifacts.

Required change:

Editing must not be tied only to `bodyText`.

The detail view should have edit modes per section:

- edit title;
- edit body/source text;
- correct transcript;
- edit summary;
- review action items;
- manage tags;
- edit context fields;
- manage links.

---

### Problem 2 — Transcript is not treated as user-correctable knowledge

Transcript is one of the most important artifacts.

Users must be able to:

- view transcript clearly;
- correct transcript;
- mark correction as user-owned;
- keep original transcript or diff if needed;
- trigger re-analysis from corrected transcript;
- prevent AI from overwriting corrected transcript.

Required UX:

```text
Transcript section
- View
- Edit transcript
- Save correction
- Re-analyze from corrected transcript
- Show original/AI transcript if developer or history mode
```

---

### Problem 3 — Analysis/summary is shown as output, not as reviewable knowledge

AI analysis should not feel like immutable truth.

Users need controls to:

- accept summary;
- edit summary;
- reject summary;
- ask for re-analysis;
- convert action item to task;
- mark a doubt as resolved;
- protect edited fields from overwrite.

Required UX:

```text
AI Analysis section
- Generated by AI badge
- Edit / Accept / Re-run
- Field-level ownership indicators
- Suggestions appear as suggestions until accepted
```

---

### Problem 4 — Project signals need explicit disposition

Project signals are visible, but visibility is not enough.

Signals should have actions:

- accept;
- dismiss;
- convert to task;
- convert to project risk;
- mark as doubt;
- resolve;
- link to supporting item;
- show provenance.

Required UX:

```text
Signal card
- Why am I seeing this?
- Source items
- Accept / Dismiss / Convert
- Status: new, accepted, dismissed, resolved
```

---

### Problem 5 — Context metadata is read-only

Context fields are displayed, but users must be able to fix them.

Examples:

- wrong date;
- wrong project;
- wrong imported title;
- wrong source type;
- wrong calendar association;
- wrong tags;
- wrong language/locale;
- wrong item type.

Required UX:

```text
Context section
- Edit metadata
- Move to project
- Change item type
- Change date
- Manage tags
- Manage source/origin
```

---

### Problem 6 — Provenance exists but is not visible enough

The code marks user-created/user-edited fields in `NoteEditorView`, which is excellent.

But the UI should show this concept.

Recommended visible indicators:

```text
AI generated
User edited
Protected
Needs review
Suggested change available
```

This is core to the product philosophy:

> The information is yours. The process is yours.

---

### Problem 7 — Imported content may skip user review

The import flow stages some imports and then enqueues processing.

The risk is that extracted text/OCR/imported metadata becomes accepted without a review step.

Required UX:

```text
Import review screen
- original file name
- detected type
- extracted title
- extracted text preview
- project assignment
- tags
- process now toggle
- save as draft/unprocessed
```

---

## 6. Recommended Information Architecture

Each item detail should be organized into explicit sections:

```text
1. Header / Identity
2. Source / Original Capture
3. Transcript / Extracted Text
4. AI Summary / Analysis
5. Actions / Tasks / Decisions
6. Context / Metadata
7. Links / Backlinks
8. History / Provenance
9. Exports / Debug
```

Each section should clearly indicate:

- source of data: user, import, audio, OCR, AI, system;
- editability;
- whether field is protected;
- whether AI has pending suggestions;
- last updated time;
- retry/reprocess availability.

---

## 7. Editing Model Recommendation

Avoid one giant edit mode.

Use section-level editing.

### Section editing examples

```text
Title: inline edit
Transcript: edit transcript sheet
Summary: edit summary sheet
Action items: convert/edit task list
Tags: tag manager sheet
Context: metadata sheet
Relations: link manager sheet
```

### Why

Different fields have different consequences.

Editing a transcript should trigger re-analysis.

Editing a title should not.

Editing a tag should not rewrite content.

Editing a summary should protect the summary from AI overwrite.

---

## 8. Protection / Ownership Rules

When user edits a field:

```text
field owner becomes user
field becomes protected
future AI output becomes suggestion, not overwrite
```

This should apply to:

- title;
- bodyText;
- transcript;
- summary;
- action items;
- task descriptions;
- tags;
- project intention;
- context metadata.

The UI should support:

```text
Protected field
AI suggested update available
Review suggestion
Accept / Reject / Merge
```

## 10. Broken or Risky Patterns to Investigate Next

### Pattern A — `try?` hides failed user-visible saves

Many UI operations use `try?`.

Risk:

- user taps Save;
- save fails;
- UI dismisses or appears successful;
- data not persisted.

Need audit:

- note save;
- project intention save;
- graph edge creation;
- imports;
- project add item;
- processing enqueue.

---

### Pattern B — processing output can overwrite user edits

There is a warning before reprocess, but we need to verify actual enforcement.

Need audit:

- transcript overwrite behavior;
- analysis overwrite behavior;
- bodyText overwrite behavior after OCR/import;
- summary overwrite behavior;
- field provenance enforcement.

---

### Pattern C — data exists in artifacts but not UI

Transcript and analysis are loaded from artifact files.

Need audit all artifacts:

- transcript.json;
- analysis.json;
- raw analysis JSON;
- processing reports;
- recording manifest;
- audio render status;
- OCR outputs;
- import metadata.

Question:

> Can the user see each meaningful artifact, or only the developer?

---

### Pattern D — edit entry points are inconsistent

Some editing happens inline, some in sheets, some hidden behind toolbar conditionals.

Need design standard:

```text
all important item fields have visible edit/review actions
all AI-generated sections have review semantics
all user-edited sections show ownership/protection
```

## 12. Acceptance Criteria for Good UI Data Ownership

The UI is acceptable when:

- [ ] User can always see the original captured/imported data.
- [ ] User can see what AI generated.
- [ ] User can distinguish AI-generated vs user-edited fields.
- [ ] User can edit title for every item type.
- [ ] User can correct transcript/extracted text.
- [ ] User can edit/accept/reject summary.
- [ ] User can convert action items to tasks.
- [ ] User can manage tags and project assignment.
- [ ] User can edit context metadata.
- [ ] User can manage links/backlinks.
- [ ] User edits are protected from overwrite.
- [ ] AI updates to protected fields become suggestions.
- [ ] Save failures are visible.
- [ ] Processing failures are recoverable.
- [ ] No meaningful artifact exists only as hidden JSON unless it is developer-only.

## 13. Immediate Recommendations

### Recommendation 1 — Make title always editable

Do not tie item editing to `bodyText != nil`.

Title is universal.

### Recommendation 2 — Add transcript correction

Transcript should become a first-class editable section.

### Recommendation 3 — Add AI analysis review controls

Summary, action items, doubts, risks, and signals need accept/edit/reject workflows.

### Recommendation 4 — Add visible provenance badges

Show:

```text
AI generated
User edited
Protected
Needs review
```

### Recommendation 5 — Add metadata editor

Allow editing:

- date;
- project;
- tags;
- item type;
- source;
- language/locale.

### Recommendation 6 — Replace silent `try?` in user save paths

User-visible save actions should show errors if they fail.

---

## 14. Summary

The current UI is already content-rich, but not yet ownership-rich.

The next product step is not just showing more information.

The next product step is making every important piece of information answer these questions:

```text
Where did this come from?
Can I edit it?
Will my edit be protected?
What will AI do with it next?
Can I review AI's changes before they overwrite anything?
```

That is the difference between a passive AI notes app and a user-owned knowledge system.
